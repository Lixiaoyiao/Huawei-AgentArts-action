# v0.9.2 fixed-runtime capability and dependency audit

This audit uses the published `@deepseek-ai/dsh@0.2.0-rc.2` npm family. It
does not propose an upstream upgrade, modify DSH internals, or count the
Headless NDJSON projection as a resumable Session log. It supplements the
[migration audit](dsh-0.2.0-rc.2-migration.md) and the Action's
[security boundary](../SECURITY.md).

## Decision

| Capability                                    | Published rc.2 evidence                                                                                                        | v0.9.2 outcome                                                                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Text task and selected text context files     | Headless accepts one task string; the Action can bound, read, and frame selected text before passing it to the existing runner | Implemented in the Action without changing DSH                                                                         |
| Real Session adoption in a new worker         | Public `--session-id`, `sessionQuery.observeSession`, and `agents.resume` exist and restore the durable Session                | Cross Actions run Resume deferred: Action storage, provenance, current authority, and conflict protocol are unfinished |
| Real image input to this Headless entry point | Public Headless input consists of `task`, `sessionId`, and `json`; it creates one text content block                           | Deferred: the fixed upstream Headless entry point has no structured image or attachment input                          |
| Office or other binary attachment input       | Lower-level file references are projected into file handle text and need stored bytes plus readable execution-world paths      | Deferred; text file context is not native Office or attachment support                                                 |

No public `resume`, `session-id`, image, or attachment Action input is added.
Agent Teams, Browser/Computer Use, desktop plugin management, and a new GitHub
backend remain outside this release.

The package declarations and implementation agree on these points:

- `dsh-headless/lib/types/index.d.ts` exposes `Config.sessionId`. The public
  startup parser accepts `--session-id <id>` and treats an unknown identity as
  an error; it does not silently start a fresh Session.
- `dsh-headless/lib/index.js`, `resolveAgent`, first requires
  `sessionPersistence` and `sessionQuery`, observes the exact Session, and
  calls `agents.resume`. It rejects a live same-process Agent, a selected
  Agent preset, a subagent/forked Session, a missing recorded working
  directory, or a different working directory.
- `dsh-agent/lib/types/index.d.ts`, `ResumeAgentOptions.setup`, provides a
  fresh unpublished Agent scope setup opportunity. This is a public route
  that a future Action adoption policy can use; no new session engine is
  necessary.
- `dsh-session-persistence/lib/types/index.d.ts` and the JSONL backend expose
  durable `create`/`open` handles and exclusive write ownership. The Session
  query API performs complete raw-event replay validation before adoption.
- `dsh-session-persistence-jsonl` supports current-format validation and
  conservative refusal for corruption or unsupported format generations.
  Its lock protects writers sharing one physical storage location.

## Reproducible finite Session probe

Run from an installed repository checkout:

```bash
node scripts/probe-fixed-runtime-resume.mjs /absolute/path/to/probe-result.json
```

The script launches the **official published CLI** in separate Node processes,
with distinct disposable `DSH_HOME` directories and a stable workspace path.
It copies the first worker's actual persistence directory to the second
worker, rather than reconstructing a log from comments or NDJSON events. A
deterministic local HTTP provider records that the second worker's request
contains the first user message, the first assistant message, and the new
follow-up. No real API key, GitHub credential, repository script, or remote
write is involved. Each subprocess has a 45-second deadline; the concurrency
readiness wait has a 15-second deadline; temporary directories are removed.

The probe verifies:

- Separate worker process identities, new home, and restored real history.
- Unknown identity and changed workspace rejection.
- Corrupt log, future format, selected preset, and subagent rejection before
  another model request.
- A concurrent worker using the same storage receives a write ownership
  conflict while the first worker holds its Session.
- Historical sandbox policy persists even when the new worker default is
  narrower. A Session initially created under `workspace-write`, restored in
  a worker configured with `DSH_PERMISSION_MODE=read-only`, still supplies
  `workspace-write` as the effective Session policy.

The last check is a **blocker observation**, not a permitted Action behavior.
It matches the published policy contracts: `SandboxPolicy.resolve` gives the
Session's `sandbox/mode` event precedence over the deployment default;
`PermissionPresetService.pinInitialPermission` preserves restored knob values;
the approval service likewise folds `approval/policy` from the Session.
Changing a new worker's environment alone does not establish current authority.

These are upstream API and real-process persistence probes using a local
provider, **not Live model Resume E2E** and not evidence that Action Resume is
implemented. The Action continues starting fresh Sessions.

## Why cross Actions run Resume is deferred

The upstream Session interface exists. The following unfinished work belongs
to the **Action**, so this audit does not attribute it to a missing upstream
Resume API:

1. **Trusted persistence and provenance.** `src/dsh/runtime.ts` creates a
   private disposable runtime; `disposeDshRuntime` removes its root, including
   Sessions. There is no Session export/import contract that binds stored
   bytes to an immutable workflow/run source, repository, task identity,
   compatible runtime/composition, retention limit, and bounded size.
   Restoring any cache or user-supplied artifact by name would be insufficient.
2. **Current permission recomputation.** A future Controller adoption path
   must authorize the current actor and current request, then reset or refuse
   historical sandbox/approval/permission intent before any resumed tool
   executes. The fresh public setup hook is available, but controlled and
   native policy behavior and extension interaction require qualification.
   Persisted permission selection is not current GitHub authorization.
3. **Cross-run conflicts.** DSH's local write lease is useful and was tested.
   Separate Actions workers importing separate artifact copies do not share
   that lease. A trusted generation and Actions concurrency protocol must
   prevent two copies from advancing the same logical Session concurrently.
4. **Credential exclusion and retention.** Full durable event data can contain
   task text, tool results, and external-extension output. The Action has not
   established a lossless export policy proving that credentials and sensitive
   extension data cannot enter persisted artifacts, or a verified expiry and
   deletion policy. Blindly uploading the disposable home would also include
   unrelated state and is unacceptable.
5. **GitHub side effects.** Model history must not restore a prior write grant
   or replay a prior GitHub mutation. Session identity must be integrated with
   the existing Gateway's authorization, validation, immediate revalidation,
   and unknown-outcome reconciliation across run boundaries. A transcript
   import alone does not supply this behavior.

This is a bounded engineering deferral. There is no empty feature flag, mock
Resume implementation, comment-history concatenation, or alternative Session
engine. Retention and cross-run authority remain **unqualified**, not assumed
to pass because the lower-level persistence probe succeeds.

## Why images and binary attachments are deferred

The fixed runtime already contains real lower-level image and file stores:
`dsh-attachment` offers image admission and stored references;
`dsh-attachment-local` stores and resolves durable image bytes;
`dsh-llm-deepseek` exposes Files APIs and request image handling. Thus the
claim that DSH has no image support anywhere would be inaccurate.

The narrower upstream blocker is the **published Headless entry point used
by this Action**. Its public config accepts no structured content or attachment
list. Its `run` function always submits:

```javascript
createUserMessage({ content: [{ type: "text", text: task }], source: { kind: "user" } });
```

Stdin is another task-text source; it is not a binary or structured-content
protocol. A file path written into `task` does not establish actual image
delivery. Implementing that route today would require replacing or extending
the fixed Headless driver or adding an independently qualified transport and
storage composition, outside this bounded release.

The **Action's own remaining work** is separate: `src/dsh/proxy.ts` mediates
Messages, the existing terminal-result formatter, and the mediated search
route; it deliberately rejects Files upload/discovery routes. Secure image
admission, byte/pixel budgets, artifact lifecycle, model capability handling,
and proxy Files authority would require additional validation. Sending the
Controller's real key directly to a worker would break the existing boundary
and is not a workaround.

Binary files also have a distinct contract. Published
`dsh-llm/lib/types/content.d.ts`, `projectFilesToText`, says all file blocks are
projected to handle text; providers do not receive files natively. Reading
Office content would additionally require stored bytes and admitted processing
tools. v0.9.2's selected UTF-8 text context files claim neither image nor Office
attachment support.

## Dependency advisory recheck

The official npm registry was queried again on **2026-10-03**:

```bash
npm audit --json --registry=https://registry.npmjs.org/
npm update fflate http-cache-semantics --package-lock-only --ignore-scripts --registry=https://registry.npmjs.org/
npm audit --json --registry=https://registry.npmjs.org/
npm ls --all --json
```

Normal constraint-respecting update produced **no dependency lock changes**;
no `--force`, peer relaxation, override, DSH upgrade, audit suppression, or
deleted test was used. A disposable copy of the manifest and lockfile was
installed with `npm ci --ignore-scripts --registry=https://registry.npmjs.org/`
to validate dependency metadata without altering the shared runtime. Strict
installation and `npm ls --all --json` both exited 0, with no invalid or missing
peer reported. However, both the shared installation and this fresh Windows
installation report two extraneous optional packages in the tree JSON:
`@img/sharp-wasm32@0.35.5` and `@emnapi/runtime@1.11.3`. This is disclosed as a
remaining platform dependency-tree diagnostic, not described as a spotless
tree or removed to make the result appear clean. Ignoring lifecycle scripts
here qualifies metadata only; normal runtime installation and Docker/native
smoke remain separate mandatory release gates. The audit
continues to exit nonzero with **15 findings: 6 moderate, 9 high, 0 critical**.
Ancestor findings refer to two underlying advisories:

| Advisory                                                                                                           | Installed constraint and evidence                                                                                                                                                | Residual outcome                                                                                       |
| ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| [GHSA-px8p-9vwx-vf98](https://github.com/advisories/GHSA-px8p-9vwx-vf98), fflate malformed ZIP64 denial of service | Root `fflate@0.8.3` is fixed, but published `@deepseek-ai/libreoffice-kit@0.1.5` depends on exact `fflate@0.8.2`                                                                 | The nested affected copy remains; upgrading it would violate the published exact dependency constraint |
| [GHSA-ch52-4w7c-c8xp](https://github.com/advisories/GHSA-ch52-4w7c-c8xp), cached response disclosure               | `dsh-otel@0.2.0-rc.2` → `got@14.6.6` → `cacheable-request@13.0.19` → `http-cache-semantics@4.2.0`; official npm lists no newer version and the advisory lists no patched version | No compatible published fix is available                                                               |

The generated Profile disables Session telemetry/log upload and package
inventory upload; Office paths are not enabled by default. This limits default
reachability but **does not fix either installed dependency vulnerability**.
Trusted extensions enabling Office processing, shared HTTP caching, or
telemetry consumers need their own assessment. Existing migration dependency
repairs are retained, and the residual risks stay disclosed.

Release qualification still requires all Action tests, Docker/native ecosystem
smoke, complete Core E2E, exact-main checks, formal canaries, installer release,
and clean public npm installation on the immutable release identities. This
audit does not replace any release gate.
